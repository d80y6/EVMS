## 1. Search End-to-End

### 1.1 Architecture Overview
```
Client -> API Gateway -> Event Processing Service (HTTP) -> PostgreSQL (ai_events table)
                                                           |-> pgvector for similarity search
```

The forensics search is handled by the `ForensicsService` within the event-proc service. It queries the `ai_events` table which stores AI detection events (people, vehicles, objects) generated by the analytics pipeline.

### 1.2 Data Sources
- **`ai_events` table**: Contains detection events ingested from AI analytics
  - `id`, `camera_id`, `event_time`, `object_type`, `confidence`, `bounding_box` (JSONB), `track_id`, `thumbnail`, `embedding` (pgvector)
- **`ai_events.embedding`**: Vector embedding for similarity search (pgvector extension)
- Events are generated from the NATS-based detection pipeline:
  ```
  Camera -> Ingest -> AI Analytics -> NATS -> Event Processor -> ai_events
  ```

### 1.3 Two Search Modes

#### Attribute-Based Search (`SearchByAttributes`)
Table: `ai_events`
```
GET/POST /api/forensics/search
```
Parameters:
- `cameras` - Array of camera IDs to filter
- `start_time` / `end_time` - Time range (RFC3339)
- `object_classes` - Object types (person, vehicle, etc.)
- `colors` - Color filters (applied client-side, no DB column exists)
- `direction` - Direction filter (applied client-side, no DB column exists)
- `min_confidence` - Confidence threshold (default 0)
- `zone_ids` - Zone filters (applied client-side, no DB column exists)
- `track_id` - Specific track ID
- `query_text` - Text query (applied client-side, no DB column exists)
- `limit` - Max results (default 100, max 1000)
- `offset` - Pagination offset

SQL pattern:
1. Count query: `SELECT COUNT(*) FROM ai_events WHERE ...`
2. Data query: `SELECT ... FROM ai_events WHERE ... ORDER BY event_time DESC LIMIT $n OFFSET $m`

#### Vector Similarity Search (`SearchByVector`)
```
POST /api/forensics/search/vector
```
Parameters:
- `embedding` - Float array for cosine similarity
- `limit` - Max results (default 100, max 1000)

SQL uses pgvector cosine distance (`<=>` operator):
```sql
SELECT ..., 1 - (embedding <=> $1::vector) as similarity
FROM ai_events
WHERE embedding IS NOT NULL
ORDER BY embedding <=> $1::vector
LIMIT $2
```

### 1.4 Findings and Risks
| Issue | Severity | Detail |
|-------|----------|--------|
| **No tenant isolation in forensics search** | HIGH | The forensics search queries `ai_events` directly without joining through `cameras -> sites` for tenant filtering. **Any authenticated user can search events from any camera across all tenants.** This is a cross-tenant data leak. |
| **Color, direction, zone, and text filters are not implemented** | MEDIUM | The `ForensicsSearchParams` struct includes `Colors`, `Direction`, `ZoneIDs`, and `QueryText` fields, but **none of these are used in the SQL query**. They are silently ignored. A user may think they are filtering by color when no such filter is applied. |
| **No bounding box spatial filtering** | MEDIUM | While the `BoundingBox` parameter exists in the `SmartSearch` RPC of the camera-mgmt service, the forensics `SearchByAttributes` does not support it. The results return bounding boxes but cannot filter by spatial region. |
| **Vector search ignores other filters** | MEDIUM | `SearchByVector` only uses the embedding for similarity. It cannot be combined with attribute filters (time range, camera, object type, etc.). |
| **No search result caching** | LOW | Every search request hits the database. Repeated identical searches within a short window are not cached. |
| **No search audit logging** | LOW | Search queries are not logged to the audit trail. There is no record of who searched for what, when, or what results were returned. |
| **Limit/offset pagination is inefficient** | LOW | Using `LIMIT/OFFSET` for pagination becomes slow on large datasets. No cursor-based pagination or keyset pagination is available. |
| **No full-text search** | LOW | `QueryText` is not implemented. There is no full-text search capability against detection metadata or annotations. |

## 2. Track Path Visualization

### 2.1 TrackPath Implementation
```
GET /api/forensics/tracks/{track_id}
```

`ForensicsService.GetTrackPath(trackID)`:
```sql
SELECT camera_id, event_time, bounding_box
FROM ai_events
WHERE track_id = $1
ORDER BY event_time ASC
```

Returns a `TrackPoint` array:
```json
{
  "track_id": "uuid",
  "path": [
    {"camera_id": "cam1", "timestamp": "2026-01-01T12:00:00Z", "bbox": [0.1, 0.2, 0.3, 0.4]},
    {"camera_id": "cam2", "timestamp": "2026-01-01T12:01:00Z", "bbox": [0.5, 0.6, 0.7, 0.8]}
  ]
}
```

### 2.2 Track Generation (in Tracker)
The `Tracker` in `event-proc/main.go` generates track IDs using IoU (Intersection over Union) matching:
- Threshold: 0.3 IoU
- Timeout: 3 seconds (tracks stale after 3s no detections)
- Matching: Detections matched to existing tracks if same label AND IoU > 0.3
- New tracks created with `uuid.New().String()` when no match found

### 2.3 Findings and Risks
| Issue | Severity | Detail |
|-------|----------|--------|
| **Track ID format inconsistency** | MEDIUM | The `Tracker` generates track IDs via `uuid.New().String()` in-memory, but the `ai_events` table stores track IDs that may come from external AI analytics. If track IDs are also assigned by the AI system, there may be two different track ID schemes coexisting. |
| **Track path only shows events, not inter-event trajectory** | LOW | The track path returns discrete detection events. There is no interpolation between points, no speed/direction calculation, and no path smoothing. |
| **No track path limit** | MEDIUM | A long-duration track could return thousands of points. There is no limit, no downsampling, and no pagination on the track path endpoint. |
| **Single-camera tracks only** | MEDIUM | The current `Tracker` matches detections within a single camera. Cross-camera tracking (following a person across multiple cameras) is not implemented. The `TrackPoint.camera_id` field suggests it was designed for this, but the matching logic is per-camera. |
| **No tenant isolation on track path** | HIGH | `GetTrackPath` does not verify that the requesting user has access to the cameras involved in the track. A user could enumerate track IDs to discover events from cameras they shouldn't have access to. |

## 3. Evidence Creation from Search

### 3.1 Evidence Flow
The evidence management system lives in the **export service** and is separate from the forensics search:

```
Forensics Search (event-proc) --> Export (JSON/CSV)
                                        |
                                        v
Evidence Management (export service)
  - Cases
  - Lockers
  - Items
  - Share Access
```

### 3.2 Evidence Endpoints (export service)
| Endpoint | Method | Purpose |
|----------|--------|---------|
| `/api/evidence/cases` | GET/POST | List/create evidence cases |
| `/api/evidence/cases/{id}` | GET/PUT/DELETE | Manage specific case |
| `/api/evidence/lockers` | GET/POST | List/create digital lockers |
| `/api/evidence/lockers/{id}` | GET/PUT/DELETE | Manage specific locker |
| `/api/evidence/items` | GET/POST | List/create evidence items |
| `/api/evidence/items/{id}` | GET/PUT/DELETE | Manage specific item |
| `/api/evidence/share/{id}` | GET/POST/DELETE | Share access management |

### 3.3 Findings and Risks
| Issue | Severity | Detail |
|-------|----------|--------|
| **No direct link between forensics search and evidence** | HIGH | The forensics search results (attribute or vector) cannot be directly converted to an evidence item. The user must manually export to JSON/CSV and then manually create evidence. There is no "Create Evidence from Search" workflow. |
| **No tenant isolation on evidence endpoints** | MEDIUM | Evidence endpoints use `JWTAuthMiddleware` only (any authenticated user). There is no check that a user's evidence is scoped to their tenant. |
| **No chain of custody** | MEDIUM | The evidence system tracks cases, lockers, and items but there is no chain of custody logging. No record of who viewed, exported, or modified evidence items. |
| **No evidence hash verification at rest** | LOW | The export endpoint generates a SHA-256 hash of the exported file, but there is no periodic verification that evidence files on disk match their recorded hash. |
| **No evidence expiration** | LOW | Evidence items have no automatic expiration. They persist indefinitely unless manually deleted. |
| **No evidence pin/approval workflow** | LOW | There is no workflow for marking evidence as "locked" or "approved" to prevent modification after a certain point. |

## 4. Incident Creation from Evidence

### 4.1 Incident System (event-proc)
The incident management system is part of the event-proc service:

| Endpoint | Purpose |
|----------|---------|
| `/api/incidents` | List/create incidents |
| `/api/incidents/{id}` | Get/update/delete incident |
| `/api/alerts` | Alert management with workflow |
| `/api/rules` | Rule engine for automated actions |
| `/api/alert-rules` | Alert rule CRUD |

### 4.2 Incident Model
Incidents are stored in the database with CRUD handlers in `incident.go`. The alert workflow supports:
- Alert creation
- Escalation (configurable timeout, default 5 minutes)
- Webhook notifications on escalation

### 4.3 Alert Rule Engine
- Rules match on: camera_id, object_type, confidence, zone polygon
- Actions: webhook, alert, notification
- In-memory rule cache with DB persistence

### 4.4 Findings and Risks
| Issue | Severity | Detail |
|-------|----------|--------|
| **No direct forensics-to-incident workflow** | HIGH | Forensics search results cannot be directly promoted to incidents. There is no "Create Incident from Detection" button or API. An operator must manually create an incident and reference the detection. |
| **Incidents not linked to evidence** | HIGH | There is no linking mechanism between incidents (event-proc) and evidence (export service). An incident report cannot reference the supporting evidence items. |
| **No bulk incident creation** | MEDIUM | Forensics searches may return hundreds of results. There is no "Select All" -> "Create Incident" workflow for bulk incident generation. |
| **Alert rules lack temporal recurrence** | MEDIUM | Alert rules match individual detections. There is no support for "alert if X detections within Y minutes" (temporal aggregation). This can cause alert storms during busy periods. |
| **Rule evaluation race condition** | LOW | `GetMatching` iterates the rule map without any ordering. Rules are evaluated non-deterministically when multiple rules match the same detection. |

## 5. Export Functionality

### 5.1 Forensics Export
```
POST /api/forensics/export
```
- Accepts search parameters + format ("json" or "csv")
- Returns file with Content-Disposition header
- CSV columns: event_id, camera_id, timestamp, track_id, class, confidence, bbox
- JSON: Full ForensicsResult array indented

### 5.2 Video Export
```
POST /api/export
```
- FFmpeg-based video segment merging (see Recording Validation Report Section 4)
- SHA-256 checksum generation
- Evidence management endpoints for organized storage

### 5.3 Findings and Risks
| Issue | Severity | Detail |
|-------|----------|--------|
| **No tenant isolation on forensics export** | HIGH | The forensics export endpoint searches without tenant filtering. Exported data can contain events from cameras across all tenants. |
| **No export rate limiting** | LOW | Export requests are not rate-limited. A user could request multiple large exports simultaneously, consuming server resources. |
| **No async export for forensics data** | LOW | Like the video export, the forensics JSON/CSV export is synchronous. For large result sets, the HTTP request blocks until complete. |
| **No export size limit on forensics** | LOW | The forensics export uses the same search parameters which have a max limit of 1000 results, so this is self-limiting. However, the video export (`/api/export`) has no limit on time range. |
| **CSV export unreliable for BBox** | MEDIUM | The bounding box array is JSON-marshaled and embedded in a CSV cell. This can break CSV parsing if the array contains commas or if the cell is not properly quoted. CSV parsers may misinterpret the brackets and commas as additional columns. |
| **No evidence creation from export** | MEDIUM | Exporting search results produces a downloadable file but does not automatically create an evidence item, case, or locker entry. The user must separately navigate to the evidence management UI to catalog the export. |

## 6. End-to-End Forensics Workflow Map

```
   AI Analytics Detection
          |
          v
   NATS: camera.{id}.events
          |
          v
   Event Processor (handleCameraEvent)
     |-- Tracker.matchDetections() -> tracks
     |-- Alert rule evaluation
     |-- Intrusion/loitering/abandoned detection
     |-- Heatmap recording
     |-- ai_events DB insert (external, via detection pipeline)
          |
          v
   Forensics Search (ai_events)
     |-- Attribute search (cameras, time, type, confidence, track)
     |-- Vector similarity search (pgvector)
     |-- Track path visualization
     |-- Export to JSON/CSV
          |
          v
   [MANUAL GAP] --> Evidence Management (Cases/Lockers/Items)
                       |
                       v
   [MANUAL GAP] --> Incident Management
```

### Key Gaps in the Workflow
1. **Detection to Search**: OK - events flow through NATS to ai_events table
2. **Search to Export**: Manual - user must export, then manually create evidence
3. **Evidence to Incident**: No link - two separate systems with no integration
4. **Search to Incident**: No path - incidents can't be created from search results directly
5. **Tenant Isolation**: Missing in forensics search (present in other areas)

## 7. API Gateway Routing for Forensics

The API Gateway routes `/api/forensics/` to the event-proc service:
```
case strings.HasPrefix(path, "/api/forensics/"):
    g.rateLimiter.rateLimitMiddleware(g.authMiddleware(func(w, r) {
        g.alertProxy.ServeHTTP(w, r)
    }))(w, r)
```

The event-proc admin server registers these handlers:
```go
mux.Handle("/api/forensics/search", ...)        // HandleSearch (POST)
mux.Handle("/api/forensics/search/vector", ...)  // HandleVectorSearch (POST)
mux.Handle("/api/forensics/tracks/", ...)        // HandleTrackPath (GET)
mux.Handle("/api/forensics/export", ...)         // HandleExport (POST)
```

### Routing Findings
- All forensics endpoints use `JWTAuthMiddleware` (any authenticated user). No role enforcement.
- No rate limiting beyond the gateway's global rate limiter.
- No per-endpoint authorization (e.g., "viewer" can search but only "operator" can export).

## 8. Summary of Critical and High Findings

1. **[HIGH] No tenant isolation in forensics search**: `SearchByAttributes` and `SearchByVector` query `ai_events` directly without tenant filtering. Cross-tenant data leak.

2. **[HIGH] No tenant isolation on track path**: `GetTrackPath` does not verify user access to the cameras in the track.

3. **[HIGH] No tenant isolation on forensics export**: Exported data can contain events from cameras across all tenants.

4. **[HIGH] No direct forensics-to-evidence workflow**: Search results cannot be promoted to evidence items.

5. **[HIGH] No incident-to-evidence linking**: Incidents and evidence are in separate services with no integration.

6. **[HIGH] No direct forensics-to-incident workflow**: Detections from search cannot be converted to incidents.

7. **[MEDIUM] Unused filter parameters**: `Colors`, `Direction`, `ZoneIDs`, `QueryText` fields exist in the search params struct but are **never applied** to the SQL query. Users get unfiltered results.

8. **[MEDIUM] Vector search ignores all attribute filters**: Cannot combine similarity search with camera/time/type filters.

9. **[MEDIUM] No search audit logging**: No record of who ran what forensics searches.

10. **[MEDIUM] Cross-camera tracking not implemented**: Track matching is per-camera only, despite the multi-camera path data model.
